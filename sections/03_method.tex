\section*{3. Method: collaborative agentic biological research}
\subsection*{3.1 Framework overview}
AI4AI4Cell takes a task specification, an initial predictor, an editable design space and data held by $K$ participating laboratories. The task specification defines prediction inputs and outputs, scorer and computational budget. Each laboratory maintains training and development partitions. A research controller proposes a design, a shared training service fits its parameters across laboratories, and local evaluators return development measurements to a coordinator. The outputs are the selected design with fitted parameters and an ordered history of proposals and outcomes (Figure~\ref{fig:research-interface}).

The key mechanism is the return of experimental evidence to the research process. An \emph{evidence card} links a proposed change to its executed configuration, aggregate learning trajectory and selection outcome. Successive cards form a persistent history, allowing the controller to revise its next hypothesis using both successful and unsuccessful trials. Trajectory information also guides training allocation: a candidate with promising early progress can be promoted for full validation. The outer loop decides what design to investigate and how to allocate evaluation; the inner process fits parameters for that design.

\subsection*{3.2 Evidence-guided proposal and revision}
The controller receives the task specification, current design and accumulated evidence cards. It returns a structured proposal with four fields: a \texttt{hypothesis} stating why a change should help, an \texttt{experiment} describing the comparison, an \texttt{expected\_effect} identifying the predicted metric or diagnostic response, and a \texttt{design\_id} resolving to an executable configuration. A validator checks the identifier against the task's editable design space. The configuration determines the intervention; the other fields state its rationale and anticipated outcome. Appendix A gives the JSON schema and design library.

Local evaluators return scores, losses and learning-curve diagnostics. The coordinator packages these with the proposal, selected checkpoint and acceptance decision. It retains a candidate if its mean development score exceeds the incumbent's, using lower mean loss to resolve ties. Each subsequent proposal receives the complete evidence history, including rejected directions. The research language model remains fixed; adaptation occurs in the predictive model and the designs explored by the loop.

Evidence influences two research decisions. In \emph{proposal revision}, measured history conditions the next design. In \emph{training allocation}, short learning trajectories determine which designs receive full validation. The latter uses a screening--promotion--validation policy that retains candidates with strong current scores as well as improving trajectories. These decisions share the evidence interface and are evaluated separately: proposal-history comparisons assess design selection, while fixed-slate racing isolates evidence-dependent allocation. Section 4 and Appendix A specify budgets and promotion rules.

\subsection*{3.3 Local fitting and distributed evaluation}
For a selected design, laboratory workers start from shared parameters and fit them on local training partitions. The coordinator combines returned parameters using training-example weights, following FedAvg \citep{McMahan2017}, with optional server momentum specified by the design. The resulting predictor is distributed for the next round. This training pipeline is unchanged across task families; adapters define the input representation, prediction head and loss.

Development evaluation gives each laboratory equal weight. If $s_i(a)$ is laboratory $i$'s development score for design $a$, the selection score is $S(a)=K^{-1}\sum_{i=1}^{K}s_i(a)$. Training-example weights determine parameter aggregation; equal-laboratory weights determine design and checkpoint selection. Every candidate starts from the same task-specific initialization for its seed. At completion, the selected checkpoint is fixed and evaluated by the held-out scorer.

Workers return parameter updates and example counts for training, and scalar scores and diagnostics for research feedback. The language model receives aggregate evidence cards. Raw interaction rows, proteomic profiles and expression responses remain at the worker interface. Experiments simulate these roles on one host, using $K=10$ for the main comparison and varying $K$ in the sensitivity study.
